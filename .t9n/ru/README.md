# in-html

Веб-приложения, каждое из которых поставляется как **один самодостаточный HTML-файл**: без зависимостей, без CDN, без
установки, без учётной записи. 49 приложений примерно на 90 общих библиотеках; исходники — обычные ES-модули. По
умолчанию сборка (`singlefile.js`) выпускает для каждого приложения два артефакта:

- `<app>/html@5-singlefile/<page>.html` — каждая страница одним самодостаточным, очищенным tree-shaking и
  минифицированным файлом, который можно открыть с диска, отправить по почте, унести на флешке или выложить на любой
  статический хостинг;
- `<app>/html@5/` — многофайловая копия для развёртывания: страницы, модули приложения и только те модули библиотек,
  которые они используют (подпапками), каждый модуль очищен и минифицирован отдельно — для статического хостинга с
  кешируемыми файлами.

Однофайловые страницы также публикуются на Codeberg Pages и GitHub Pages под короткими именами (`LANDING.html`,
`RESUME.html`, `DOCS.html`, `CRYPTO.hashing.html`, …), каждое приложение — как офлайн-демо (`demo/<slug>.html`), а
курсы CSS — как страницы с живыми примерами (`course/in-html/`).

> **Учебный курс на русском.** Оглавление курсов по HTML, CSS и JavaScript:
> [.t9n/ru/LEARN_COURSE.md](https://codeberg.org/slnknrr/in-html/src/branch/all-in-one/.t9n/ru/LEARN_COURSE.md).

Вместо этого приложение может назвать свои артефакты **NOTICE-файлами** — само наличие файла и есть запрос
(`targets.js`):

| NOTICE-файл в `<app>/` | артефакт |
| --- | --- |
| `OFFLINE_NOTICE.md` | `html@5_offline/` — многофайловая копия, вовсе без сетевого кода |
| `SINGLEFILE_OFFLINE_NOTICE.md` (или `OFFLINE_SINGLEFILE_…`) | `html@5_offline_singlefile/<page>.html` — по файлу на страницу, без сетевого кода |
| `SERVERLESS_NOTICE.md` | `html@5_serverless/` — статический сайт для любого статического хостинга (маршруты через `404.html`) |
| `SINGLEFILE_SERVERLESS_NOTICE.md` | `html@5_serverless_singlefile/<app>.mjs` — один скрипт для Node ≥ 18, который отдаёт сайт как GitHub Pages |
| `BACKEND_NOTICE.md` | `html@5_backend/` — `server.mjs` + `backend.mjs` (собранный `<app>/backend.js`) + `public/` |
| `SINGLEFILE_BACKEND_NOTICE.md` | `html@5_backend_singlefile/<app>.mjs` — сервер, бэкенд и страницы в одном скрипте для Node ≥ 18 |
| `STANDALONE_NOTICE.md` | `html@5_standalone/<page>.html` — один файл, который открывается из file:// и общается с серверами по HTTPS + CORS (без предустановленного сервера) |
| `ELECTRON_NOTICE.md` | `html@5_electron/` — настольное приложение для Electron ≥ 29: `package.json` (`npm start` = `electron .`), `main.mjs` (страницы из приватной схемы `in-html://<app>/`, собранный `<app>/backend.js` внутри процесса), `preload.cjs` (небольшой мост `window.inHtmlElectron`), `public/` |
| `SINGLEFILE_ELECTRON_NOTICE.md` | `html@5_electron_singlefile/` — то же, но бэкенд и однофайловые страницы внутри `main.mjs` |

Каждая страница узнаёт свой артефакт из `globalThis.IN_HTML_ARTIFACT = { mode, singlefile, servers }`. Офлайн-артефакты
подменяют модули, у которых есть двойник `x.offline.js` (например, `rooms/client.offline.js`), поэтому сетевого кода в
них нет; генерируемые серверы — это `hosting.js` (Node ≥ 18, без зависимостей) плюс `backend.js` приложения;
Electron-артефакты запускают те же `hosting.js` и `backend.js` в главном процессе Electron (`electron.js`), так что
настольная сборка обращается к тому же `/api`, что и серверная. Electron пользователь ставит сам (`npx electron .` в
папке артефакта); у репозитория нет npm-зависимостей.

Как устроен репозиторий (папки, библиотеки, движок, сборка, CI), описано в
[ARCHITECTURE.md](https://codeberg.org/slnknrr/in-html/src/branch/all-in-one/ARCHITECTURE.md).

> **Где он живёт.** Источник — [codeberg.org/slnknrr/in-html](https://codeberg.org/slnknrr/in-html);
> [github.com/slnknrr-dev/in-html](https://github.com/slnknrr-dev/in-html) — зеркало только с кодом. Собранные страницы
> раздаются и с Codeberg Pages, и с GitHub Pages.

## in-html и in-javascript

Два репозитория — две половины одной работы:

| | [in-javascript](https://codeberg.org/slnknrr/in-javascript) | **in-html** (этот репозиторий) |
| --- | --- | --- |
| предмет | язык: структуры данных, алгоритмы, порты, поведение среды выполнения | веб: приложения, браузер, пограничные случаи веб-разработки |
| первый приоритет | R&D — наивные и канонические реализации, затем другие парадигмы | frontend-first — рабочее, приятное приложение |
| бэкенд | основы и компоненты | серверы, с которыми поставляются приложения (`hosting.js`, `backend.js`) |
| стиль кода | выразительный JS: модули, метапрограммирование, переиспользование | простой, программный, умеренный JS, который служит странице |
| сборка | `downgrade.js`: один сниппет → артефакты для ES3 … ES2025, node 4 … 24 | `singlefile.js`: одно приложение → одиночные файлы, статические сайты, серверы, настольные приложения |

**Красивый JavaScript живёт в in-javascript; красивый, удобный frontend-first веб — здесь.** Код в этом репозитории
нарочно написан под это: он не импортирует сниппеты и не следует их метапрограммному стилю. Это прямолинейный код, по
которому читатель может пройти от обработчика события до DOM. Идеи переходят между репозиториями; код для каждой
стороны пишется заново. Браузерный JavaScript и портфолио веб-разработчика оценивать здесь; сам язык — в in-javascript.

## Классы приложений

| класс | альтернатива | описание |
| --- | --- | --- |
| frontend | client | Строго зависит от бэкенда: привязан к конкретному API; без него ничего не отображается и не работает. |
| spa | unhosted | Не зависит от сервера: работает в браузере. Для запуска может понадобиться локальный HTTP-сервер (CORS / модули), но данные хранит у пользователя, а не на бэкенде. |
| pwa | unhosted | Клиент с запасным режимом SPA: полноценный клиент, но когда сеть пропадает, Service Worker переводит приложение в автономный режим SPA. |
| **isomorphic** | **unhostedable** | Клиент с запасным режимом обнаружения: продвинутый гибрид. Он ищет **центральный API, а если его нет — начинает самообнаружение** локальной инфраструктуры. |
| standalone | – | Ноль fetch / ноль серверов: полностью автономное приложение. Никогда не обращается к серверам через `fetch`. Работает из `file://`. |

Суффикс папки приложения объявляет его класс, и сборка это соблюдает
([policy.js](https://codeberg.org/slnknrr/in-html/src/branch/all-in-one/policy.js)):

| суффикс | класс | правило сборки |
| --- | --- | --- |
| `-offline`, `-effect` | standalone | артефакт не должен содержать ни сетевого API, ни удалённых ресурсов, иначе сборка падает |
| `-serverless` | spa / unhosted | данные остаются у пользователя; запросы, которые настраивает пользователь, разрешены и попадают в отчёт |
| `-pwa`, `-isomorphic` | pwa / isomorphic | попадает в отчёт |
| другой | client | попадает в отчёт |

Теперь папки приложений обходятся без суффикса и объявляют свои артефакты NOTICE-файлами: цель `OFFLINE` NOTICE
(`html@5_offline/`, `html@5_offline_singlefile/`) подчиняется тому же правилу нулевой сети, что и суффикс standalone,
как бы ни называлась папка. Столбец *класс* ниже говорит, чем приложение является.

## Сборка и проверка

Node ≥ 22.12 (или Bun); устанавливать нечего — парсер, бандлер, минификаторы и сборщик лежат в корне репозитория.

```bash
node singlefile.js
```

```bash
node check.js
```

Первая команда собирает каждое приложение в артефакты, названные его NOTICE-файлами; вторая запускает проверки,
которым не нужен браузер (связи модулей, модульные тесты библиотек, сетевой аудит артефактов, Electron-артефакты).
`node server.js` раздаёт исходники для разработки; `node check.js page | e2e | golden` управляют headless Chrome / Edge.

CI на обеих сторонах делает одно и то же: Forgejo Actions на Codeberg собирают, доказывают воспроизводимость вывода,
проверяют, коммитят артефакты и публикуют страницы, демо и курсы на Codeberg Pages; GitHub Actions на зеркале делают те
же проверки и разворачивают то же дерево на GitHub Pages, ничего не коммитя.

Все команды, флаги, артефакты, NOTICE-файлы, конвейер и обе настройки CI:
[README_FOR_DEVOPS.md](https://codeberg.org/slnknrr/in-html/src/branch/all-in-one/.t9n/ru/README_FOR_DEVOPS.md).
